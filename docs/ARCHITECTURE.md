# Architecture Guidelines

This project uses Next.js with the App Router (`src/app`) and a Feature-Sliced Design pattern.

## Directory Structure

- `src/app/`: Only contains route definitions, pages, layouts, and loading/error states. **Do not put business logic here.**
- `src/features/`: Contains domain-specific business logic. Each feature folder (e.g., `auth`, `admin`) encapsulates its own:
  - `components/` - Feature-specific UI
  - `services/` - API requests for this feature
  - `hooks/` - Feature-specific React hooks
  - `store/` - Feature-specific state (Zustand)
  - `validations/` - Zod schemas
  - `types.ts` - TypeScript interfaces
- `src/components/`: Globally shared UI components.
  - `ui/`: Shadcn primitive components.
  - `layout/`: App layout components (Navbar, Sidebar).
  - `shared/`: Generic, cross-feature components.
- `src/lib/`: Global utility functions.

## Routing & Role-Based Access Control (RBAC)

The application implements a strict Role-Based Access Control (RBAC) system with primary roles including `SUPER_ADMIN`, `ADMIN` (Operational Admin), and `COMPANY_ADMIN` (Corporate B2B).

- The app uses route groups for layout organization and role segregation:
  - `(auth)` for authentication pages (`/login`). Shared across all admin roles.
  - `(strive_wheels)/admin` for all StriveWheels Operational/Super Admin routes (e.g., `/admin/users`, `/admin/bookings`). Requires `SUPER_ADMIN` or `ADMIN` role.
  - `(strive_wheels)/company` for all Company Admin routes (e.g., `/company/employees`, `/company/riders`). Requires `COMPANY_ADMIN` role.
- **Route protection is strictly enforced via Next.js Edge Middleware (`middleware.ts`)**. 
  - Upon login, a `user_role` cookie is generated alongside the authentication tokens.
  - The middleware intercepts every request, reads the `user_role` cookie, and securely redirects users to their designated portals if they attempt to access an unauthorized route segment. Client-side `<RoleGuard>` wrappers are not needed on individual pages.

## New Feature Implementation

When adding a new major feature (e.g., "Invoices", "Products"), follow this strict file creation sequence to build from the data layer up to the view layer:

1. **Types (`src/features/<feature-name>/types.ts`)**: Define TypeScript interfaces for data models and API responses.
2. **Mock Data (`src/features/<feature-name>/data/mockData.ts`)**: Create mock data to simulate the API response for rapid frontend development.
3. **API Services (`src/features/<feature-name>/services/`)**: 
   - `[feature]Endpoints.ts`: Define API route constants.
   - `[feature]Api.ts`: Create the Axios/fetch wrapper. Use a `USE_MOCK_DATA` toggle to switch between mock data and the real `apiService`.
4. **Hooks (`src/features/<feature-name>/hooks/`)**: Write React Query hooks (`useQuery`, `useMutation`) to wrap the API service calls, handling caching and state.
5. **Components (`src/features/<feature-name>/components/`)**: Build the UI components (e.g., Tables, Dialogs). Assemble them into a single main client component (e.g., `InvoicesClient.tsx`).
6. **Page (`src/app/(dashboard)/<route>/page.tsx`)**: Create the Next.js page that imports the main client component and acts as the route entry point.

## Pages and Components

- **Pages**: Placed exclusively inside `src/app/`. Pages should act primarily as glue—they fetch server-side parameters/search parameters and pass them down into Client or Server components imported from `src/features/`.
- **Feature Components**: UI pieces tied to specific business logic (e.g., `InvoiceList`, `CreateProductForm`) must reside inside `src/features/<feature-name>/components/`. They should handle their own internal state and data fetching if necessary.
- **Component Size Limit**: Never cross 300 lines of code in a single file. If a component goes above this limit, you must refactor and split it into smaller, manageable sub-components.

## Global Components (`src/components/`)

Global UI components are organized into the following categories:

- **`ui/`**: Base primitive elements (like Buttons, Dialogs, Inputs) generated by `shadcn`. They should remain completely agnostic and re-usable. Do not modify these to handle business logic.
- **`forms/`**: Reusable form input wrappers (e.g., `TextInput`, `SelectInput`, `DateInput`) that integrate with form libraries like React Hook Form.
- **`layout/`**: Application layout shell components (e.g., `Navbar`, `Sidebar`).
- **`providers/`**: Global React Context providers (e.g., theme, hydration guards, router providers).
- **`shared/`**: Generic components used across multiple features (e.g., `DashboardHeader`, `DeleteDialog`, `StatCard`, `FormDialogFooter`).
- **`common/`**: Additional generic components like tables and base navigations.

## Usage Examples

### DataTable

The generic `DataTable` component (`src/components/common/Table/DataTable`) handles rendering data, pagination, and row actions.

```tsx
import { DataTable } from "@/components/common/Table";

interface User {
  id: string;
  name: string;
  role: string;
}

const columns = [
  { key: "name" as const, label: "Name" },
  {
    key: "role" as const,
    label: "Role",
    render: (value: string) => <Badge>{value}</Badge>,
  },
];

const actions = [
  {
    label: "Edit",
    onClick: (row: User) => console.log("Edit", row),
  },
];

export function UserTable({ data }: { data: User[] }) {
  return (
    <DataTable
      columns={columns}
      data={data}
      actions={actions}
      itemsPerPage={10}
      showCard={true}
    />
  );
}
```
